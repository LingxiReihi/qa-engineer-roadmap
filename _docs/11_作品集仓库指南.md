# 11 · 作品集仓库指南

> **目标**：从 Day 1 开始建立 `qa-engineer-roadmap` 仓库，180 天里所有学习成果都放进去，最终成为你的**测试开发作品集**。
> **核心原则**：每一次作业提交、每一次 Code Review、每一个阶段项目，都落到这个仓库里。

---

## 一、为什么需要作品集

| 场景 | 没有作品集 | 有作品集 |
|---|---|---|
| 面试 | 「我学过 pytest」 | 「这是我的 200 个 pytest 用例，覆盖率 85%」 |
| 复盘 | 「我好像学过 Linux」 | 「git log 显示我 120 次提交，每周都有项目」 |
| 求职 | 简历一句话 | 简历附 GitHub 链接 |
| 信心 | 「我能不能做出来？」 | 「我已经做过 8 个阶段项目了」 |

**作品集 = 可验证的能力证据**。它比简历上的任何描述都有说服力。

## 五、每日提交规范

### 5.1 Commit message 格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

**type**：
- `feat`：新功能（项目代码）
- `docs`：文档
- `test`：测试用例
- `fix`：修复
- `chore`：工程杂项（配置、依赖）
- `day`：每日作业（推荐）

**scope**：阶段编号，如 `01`、`03`、`04`

**subject**：简短描述（≤ 72 字符）

**示例**：

```
day(01): implement user_mgr CRUD with exception handling

- add models.py with User dataclass
- add storage.py with JSON persistence
- add service.py with input validation
- add cli.py with interactive commands
- 10 unittest cases, coverage 85%

Review: A (need better naming in service.py)
```

```
feat(04): add login + token refresh for API tests

- implement AuthClient with auto refresh
- add 15 parametrized cases
- Allure report integrated

Review: S
```

### 5.2 每日提交节奏

```
Day X 流程：
1. 学习 → 写代码 → 写测试
2. 自测通过
3. git add . && git commit -m "day(0X): <描述>"
4. 提交作业给 AI Review
5. Review 通过后：git push
6. Review 不通过：修改后 amend commit 或新 commit
```

### 5.3 分支策略（可选，推荐 Week 4 后启用）

```
main           ← 始终可部署（合并前必须 Review 通过）
  │
  ├── day/01   ← 每日作业分支
  ├── day/02
  ├── ...
  ├── week/1   ← 每周项目分支
  ├── week/2
  └── feature/xxx  ← 功能开发
```

**Day 分支流程**：

```bash
git checkout main && git pull
git checkout -b day/01
# ... 写代码 ...
git commit -m "day(01): ..."
git push -u origin day/01
# 提 PR → Review 通过 → 合并到 main
```

## 七、CI 集成（让作品集「活」起来）

### 7.1 自动跑测试

`.github/workflows/ci.yml`：

```yaml
name: Roadmap CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.11"]
        directory:
          - 01-python/projects/user_mgr
          - 04-pytest/projects/pytest-framework
          - 05-api-automation/projects/api-test-suite
          - 07-web-mobile/projects/web-automation

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt
      - run: pytest --cov=. --cov-fail-under=70
        working-directory: ${{ matrix.directory }}
```

### 7.2 自动记录评分

CI 跑完后，把评分写入仓库的 `score-history.json`（或用 GitHub Actions artifact）：

```yaml
- name: Record score
  run: |
    echo "day:${{ github.sha }}:${{ matrix.directory }}:PASS" >> score-history.txt
    git add score-history.txt
    git commit -m "chore: record CI result" || true
    git push || true
```

## 八、作品集的用途

### 8.1 面试

- 简历上写「GitHub：github.com/xxx/qa-engineer-roadmap」
- 面试时直接打开仓库，展示：
  - 提交历史（`git log --oneline`）
  - 阶段项目（每个有 README）
  - 评分历史（README 里的评分表）
  - CI 运行记录（Actions 标签页）

### 8.2 复盘

- 每周回看：本周提交了什么？评分如何？
- 每月回看：评分趋势是上升还是下降？
- 每季度回看：技术栈覆盖了哪些？还缺哪些？

### 8.3 求职

- 简历附件：作品集 GitHub 链接
- 求职信：「这是我的 180 天测试开发学习作品集，含 8 个阶段项目、200+ 测试用例、CI/CD 集成」
- 面试官问「你有什么作品？」→ 直接打开仓库

## 九、常见陷阱

| 陷阱 | 说明 | 解决 |
|---|---|---|
| 只写代码不提交 | 作业没落盘 | 每天至少 1 次 commit |
| commit message 乱写 | 历史难读 | 用规范格式（见 §5.1） |
| 提交 .venv / .env | 仓库膨胀 / 泄露密钥 | .gitignore 配好 |
| 不更新 README | 作品集没有门面 | 每周更新评分和进度 |
| 阶段项目散落 | 找不到在哪 | 严格按目录结构放 |
| CI 不跑 | 没有持续验证 | 配置 Actions 自动跑 |
| 不分支 | 直接在 main 改 | Day/Week 分支 + PR |
| 评分不记录 | 不知道进展 | README 评分表 + score-history |

## 十、本仓库的承诺

读完这一份，你应该明白：

1. **仓库从 Day 1 开始建** —— 不等到最后才整理
2. **每个阶段一个目录** —— 成果有归处
3. **每日 commit + 每周项目** —— 进展可追踪
4. **README 是门面 + 评分表** —— 作品集有灵魂
5. **CI 自动跑测试** —— 作品集是「活的」
6. **面试时直接打开** —— 可验证的能力证据

> 「作品集不是最后写出来的，是每天提交出来的。」
