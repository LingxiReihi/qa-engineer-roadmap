## 一、性能测试在测试开发中的位置

性能测试是测试开发的"专项能力"。不是每个测试开发都做性能测试，但**会做性能测试是加分项**。

性能测试的核心是**用数据说话**：

- 接口响应时间是多少？
- 系统能支撑多少并发？
- P95、P99 是多少？
- 瓶颈在哪里？

**面试频率**：测试开发面试 20~30% 与性能测试相关。

## 四、关键知识点

### 4.1 性能测试类型

| 类型 | 目标 | 场景 |
|---|---|---|
| 负载测试 | 测试系统在特定负载下的表现 | 业务高峰 |
| 压力测试 | 找到系统极限 | 容量规划 |
| 稳定性测试 | 长时间运行是否稳定 | 7×24 运行 |
| 峰值测试 | 突发流量 | 秒杀、抢购 |
| 容量测试 | 评估扩容需求 | 大促前 |
| 基准测试 | 建立性能基线 | 版本对比 |

### 4.2 关键指标

| 指标 | 含义 | 单位 |
|---|---|---|
| 响应时间（RT） | 单次请求耗时 | ms |
| 平均响应时间 | 所有请求的平均耗时 | ms |
| P50 | 50% 请求耗时小于此值 | ms |
| P95 | 95% 请求耗时小于此值 | ms |
| P99 | 99% 请求耗时小于此值 | ms |
| TPS | 每秒事务数 | 次/秒 |
| QPS | 每秒查询数 | 次/秒 |
| 并发用户数 | 同时活跃的用户数 | 人 |
| 错误率 | 失败请求占比 | % |

> **P95/P99 比平均值更重要**：平均值会被少数慢请求拉高，P95/P99 反映真实体验。

### 4.3 Locust 概念

- **HttpUser**：定义一个用户类型
- **task**：用户要执行的操作
- **wait_time**：任务之间的等待时间
- **weight**：任务执行权重

```python
from locust import HttpUser, task, between

class WebsiteUser(HttpUser):
    wait_time = between(1, 3)

    @task
    def hello_world(self):
        self.client.get("/hello")

    @task(3)  # 3 倍权重
    def world(self):
        self.client.post("/world", json={"msg": "hi"})
```

### 4.4 Locust 架构

```
┌─────────────┐      ┌─────────────┐
│  Web UI     │─────▶│  Master     │
│  (8089)     │      │  (5557)     │
└─────────────┘      └──────┬──────┘
                            │
                   ┌────────┼────────┐
                   ▼        ▼        ▼
              ┌────────┐ ┌────────┐ ┌────────┐
              │Worker  │ │Worker  │ │Worker  │
              └────────┘ └────────┘ └────────┘
```

- **Master**：调度任务、汇总数据
- **Worker**：执行压测
- **Web UI**：控制压测、查看图表

### 4.5 性能瓶颈分类

| 类别 | 表现 | 排查工具 |
|---|---|---|
| CPU | 持续 80%+ | `top`、`htop` |
| 内存 | 持续 80%+ | `free`、`vmstat` |
| 磁盘 IO | 等待时间高 | `iostat`、`iotop` |
| 网络 | 丢包、延迟高 | `ping`、`mtr`、`netstat` |
| 数据库 | 慢查询、连接池满 | 慢查询日志 |
| 应用 | GC 频繁、线程池满 | APM 工具 |

### T6-1：响应时间分布

**任务**：理解 P50/P95/P99 的含义。

```python
import statistics

response_times = [50, 60, 55, 70, 1000]  # ms

# 平均值
avg = statistics.mean(response_times)  # 227 ms

# 中位数（P50）
p50 = statistics.median(response_times)  # 60 ms

# P95
p95 = sorted(response_times)[int(0.95 * len(response_times))]  # 1000 ms

# 95% 的用户响应时间 ≤ 1000 ms
```

**思考**：
- 为什么平均值 227 ms 会误导？
- 为什么 P95 比平均值更能反映真实体验？

**验收**：能解释 P50/P95/P99 的业务含义。

### T6-3：核心概念

**任务**：

```python
from locust import HttpUser, task, between, constant

class MyUser(HttpUser):
    wait_time = constant(2)  # 固定等待 2 秒

    @task
    def get_users(self):
        self.client.get("/users")

    @task(2)  # 权重 2，执行频率是 get_users 的 2 倍
    def get_user(self, user_id: int = 1):
        self.client.get(f"/users/{user_id}")

    @task
    def create_user(self):
        self.client.post("/users", json={"name": "Alice"})
```

**运行**：

```bash
locust -f locustfile.py --host http://jsonplaceholder.typicode.com
```

**验收**：能解释 `wait_time`、`task`、`weight` 的作用。

### T6-7：自定义指标与断言

from locust import events, HttpUser, task, between

@events.test_start.add_listener
def on_test_start(environment, **kwargs):

@events.test_stop.add_listener
def on_test_stop(environment, **kwargs):

class MetricsUser(HttpUser):

### T6-8：复杂场景

**任务**：模拟完整业务流程。

```python
from locust import HttpUser, task, between, events

class OrderFlowUser(HttpUser):
    wait_time = between(2, 5)

    @task(1)
    def browse_and_order(self):
        # 1. 浏览商品
        self.client.get("/products")

        # 2. 加入购物车
        self.client.post("/cart", json={"product_id": 1})

        # 3. 结算
        resp = self.client.post("/checkout", json={"payment": "credit_card"})
        if resp.status_code != 200:
            raise Exception("Checkout failed")

    @task(0.1)  # 10% 的用户做这个
    def cancel_order(self):
        self.client.delete("/cart")
```

**验收**：能模拟多步骤流程。

## 七、性能测试报告模板

```markdown
# 性能测试报告：订单系统

## 1. 测试背景
- **版本**：v2.3.0
- **测试周期**：2024-09-10
- **测试人员**：张三

## 2. 测试目标
- 验证系统在 500 并发下的稳定性
- 确认 P95 响应时间 < 1 秒
- 错误率 < 1%

## 3. 测试环境
| 角色 | 配置 |
|---|---|
| 应用服务器 | 4 核 8G，2 台 |
| 数据库 | 8 核 16G，MySQL 8.0 |
| 缓存 | 2 核 4G，Redis 6.0 |
| 压测机 | 8 核 16G，3 台 |

## 4. 测试场景
| 场景 | 用户比例 | 说明 |
|---|---|---|
| 浏览商品 | 60% | GET /products |
| 加入购物车 | 20% | POST /cart |
| 结算下单 | 15% | POST /checkout |
| 查询订单 | 5% | GET /orders |

## 5. 测试结果
| 并发 | TPS | P50 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|
| 100 | 450 | 120ms | 350ms | 800ms | 0.1% |
| 200 | 800 | 180ms | 500ms | 1200ms | 0.3% |
| 300 | 950 | 250ms | 800ms | 2000ms | 0.8% |
| 400 | 980 | 320ms | 1200ms | 3500ms | 2.1% |
| 500 | 850 | 400ms | 1800ms | 5000ms | 5.3% |

## 6. 瓶颈分析
- **CPU**：400 并发时 CPU 85%，接近上限
- **数据库**：连接池满，查询等待
- **慢 SQL**：`SELECT * FROM orders WHERE user_id = ?` 缺索引

## 7. 优化建议
1. 给 `orders.user_id` 加索引（预计提升 30%）
2. 增加数据库连接池大小（从 20 到 50）
3. 增加应用服务器（从 2 台到 3 台）

## 8. 结论
- 系统在 300 并发内性能达标
- 400 并发开始出现性能问题
- 500 并发下不达标，需要优化
```

## 八、常见陷阱

| 陷阱 | 说明 | 解决 |
|---|---|---|
| 压测环境太小 | 本地压不出真实瓶颈 | 用云压测或专用环境 |
| 数据量不足 | 生产库百万行，测试库千行 | 造数或同步生产数据 |
| 忽略缓存 | 缓存命中掩盖数据库问题 | 先压冷缓存再压热缓存 |
| 只看平均值 | 平均值掩盖长尾 | 关注 P95/P99 |
| 忽略错误率 | 关注 TPS 但没看错误率 | 错误率 > 1% 要排查 |
| 压测时间太短 | 5 分钟看不出动摇 | 至少 30 分钟 |
| 单点压测 | 只压一个接口 | 模拟完整业务流程 |
