## 一、为什么需要这一阶段

很多自学者跳过了测试理论，直接进入工具学习，结果：

- 写测试只会照抄正向流程
- 反向用例、边界用例全靠"感觉"
- 面试官问"你怎么设计用例"答不上来

**测试理论是测试开发的灵魂**。工具可以现学，但思维要慢慢养。

## 四、关键知识点

### 4.1 测试金字塔

```
          /\
         /UI \           ← 端到端测试（少量）
        /------\
       / 集成   \         ← 接口测试（适量）
      /----------\
     /   单元     \       ← 单元测试（大量）
    /--------------\
```

- **底层（单元）**：速度快、定位精确，应该占 70%
- **中层（接口/集成）**：验证模块协作
- **顶层（UI/E2E）**：慢、脆、维护成本高，应尽量减少

> 测试开发的核心价值：**把测试重心从顶层下沉到底层**。

### 4.2 黑盒 vs 白盒

| 维度 | 黑盒 | 白盒 |
|---|---|---|
| 关注 | 功能、需求 | 代码逻辑、分支 |
| 输入 | 需求文档 | 源代码 |
| 典型方法 | 等价类、边界值、场景法 | 语句覆盖、分支覆盖、路径覆盖 |
| 测试开发适用 | 接口、UI 测试 | 单元测试、代码审查 |

### 4.3 测试分类

- **功能测试**：是否符合需求
- **性能测试**：响应时间、吞吐、并发
- **安全测试**：SQL 注入、XSS、越权
- **兼容性测试**：浏览器、设备、系统版本
- **回归测试**：改动后旧功能是否受影响
- **冒烟测试**：核心流程能否跑通
- **探索性测试**：无固定用例的探索

### 4.4 用例设计四法

#### ① 等价类划分

把输入域划分为若干等价类，从每个类选一个代表值。

```
输入：年龄（合法范围 18~60）
等价类：
  - 有效：18~60
  - 无效：小于 18
  - 无效：大于 60
  - 无效：非数字
  - 无效：空
```

#### ② 边界值分析

边界往往最容易出错，在等价类基础上取边界值。

```
范围 [18, 60]
边界值：17, 18, 19, 59, 60, 61
```

#### ③ 场景法

针对业务流程，列出正常流、备选流、异常流。

```
登录场景：
  正常流：输入正确账号密码 → 登录成功
  备选流1：账号正确密码错 → 提示密码错误
  备选流2：账号不存在 → 提示账号不存在
  异常流：网络断开 → 提示网络异常
```

#### ④ 错误推测法

基于经验和直觉，猜测可能出错的地方。

- 空值、超长值、特殊字符
- 时区、闰年、跨日
- 并发、重复提交
- 权限、越权访问

### 4.5 判定表

当多个条件组合影响结果时使用。

```
| 条件1 | 条件2 | 条件3 | 动作 |
| V     | V     | V     | A1   |
| V     | V     | F     | A2   |
| V     | F     | *     | A3   |
| F     | *     | *     | A4   |
```

## 八、常见陷阱

| 陷阱 | 说明 | 解决 |
|---|---|---|
| 只测正向流程 | 漏掉大量异常场景 | 每个功能强制写 3 条反向用例 |
| 边界值漏测 | 只测"中间值" | 强制取 min, min+1, max-1, max, max+1 |
| 需求理解偏差 | 凭感觉写用例 | 先用"需求追溯矩阵"对齐 |
| 用例描述含糊 | "输入正确数据" | 必须给出具体值 |
| 前置条件缺失 | 用例执行不了 | 每条用例必须有前置条件 |
| 优先级滥用 | 全标 P0 | 严格按"对业务影响"分级 |
| 不评审就执行 | 用例有错才发现 | 用例评审会能省 80% 的执行时间 |
