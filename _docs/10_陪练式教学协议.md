# 10 · 陪练式教学协议

> **本文件是全路径的「方法论」文档**，与「学什么」并列决定「怎么学」。
> 配合 [README.md](./README.md) 的「学习方法论」使用。
> **核心承诺**：不代写作业；通过 Code Review 才能进入下一天。

---

## 一、核心理念

```
学习 → 实战 → 提交 → Code Review → 修正 → 验收 → 下一天
```

**与「传统自学」的根本区别**：

| 传统自学 | 陪练式 |
|---|---|
| 看完视频 = 学完 | 通过 Review = 学完 |
| 代码能跑 = 合格 | 代码好 = 合格 |
| 自己决定今天学什么 | 按 Day X 课程推进 |
| 错误无人发现 | 每天被指出 |
| 学完无作品 | 180 天攒出一套作品集 |

**两条铁律**：

1. **不代写作业** —— 可以讲思路、讲异常、讲测试点、讲优化方向，但不给最终答案。
2. **通过 Review 才进下一天** —— 代码能跑 ≠ 通过；`print("Hello")` 能跑，但不代表写得好。

---

## 二、每日固定 7 部分流程

每天开始时，对 AI 说一句：

```
开始 Day X
```

AI 会按以下 7 部分输出当天课程：

### ① 今日目标

**格式**：3~5 条，明确「今天结束应该能做到什么」。

**示例**：

```
Day 3 目标
- 能写出带默认参数和 *args/**kwargs 的函数
- 能解释可变默认参数陷阱
- 能为一个函数写 3 个单元测试（正常/边界/异常）
- 能用 pytest 运行并看懂输出
```

### ② 理论课

**原则**：只讲当天必须掌握的知识，不堆砌。

**每个概念必须包含**：
- 一句话定义
- 一个最小可运行示例
- 一个常见坑

**反例**：「函数是代码的封装单元，可以接收参数并返回结果，是模块化的基础……」（太长，没价值）

**正例**：
> `def f(a, b=1)` 中 `b=1` 是默认值。
> 坑：`def f(x=[])` 多次调用共享同一个 list。

### ③ 示例代码

**原则**：少量、能跑、标注关键点。**不直接给练习答案**。

示例代码必须：
- 带注释说明「为什么这样写」
- 至少 1 个反例（错的写法 + 错在哪里）
- 不超过 30 行

### ④ 今日练习

**类型**：10 分钟能完成的思考/编码小题。

**要求**：
- 不查资料独立完成
- 每题 ≤ 5 行代码
- 至少 1 道问答题（理解性）

### ⑤ 今日实战任务

**定位**：模拟真实测试开发工作场景。

**特征**：
- 给出需求描述，不给出实现
- 包含正常 + 异常 + 边界路径
- 与后续阶段衔接（例如「今天写的函数明天会被 pytest 测」）

### ⑥ 提交作业

**模板**（直接复制填写）：

```markdown
# Day X 作业提交

## ① 环境信息
- Python: x.x.x
- OS: Windows/macOS/Linux

## ② 代码
```python
# day03_function.py
...
```

## ③ 运行结果
```text
$ python day03_function.py
...
$ pytest -v
...
```

## ④ 测试场景（自设计）
1. ...
2. ...
3. ...

## ⑤ 练习题答案
1. ...
2. ...
3. ...

## ⑥ 遇到的问题
- 卡在哪一步：
- 尝试过什么：
- 现在状态：

## ⑦ 自评
- 完成度（%）：
- 最有把握的部分：
- 最不确定的部分：
```

### ⑦ Code Review

AI 按 7 维度给出 Review 结果。

## 三、Code Review 7 维度

| 维度 | 检查点 | 典型问题 |
|---|---|---|
| **正确性** | 功能是否符合需求；边界是否覆盖 | 除 0 未处理；空输入崩溃 |
| **代码结构** | 函数是否单一职责；模块是否分层 | 一个函数 100 行；业务逻辑混在 CLI |
| **命名** | 变量/函数/模块名是否表意 | `x`、`data`、`tmp1`；动词名词混淆 |
| **异常处理** | 是否捕获了该捕获的异常；是否吞掉了不该吞的 | `except: pass`；`except Exception` 过宽 |
| **可读性** | 是否能被第三人读懂；注释是否恰当 | 注释解释「做了什么」而非「为什么」 |
| **测试思维** | 是否考虑了正常/异常/边界/并发 | 只测正常路径；忽略空值 |
| **工程习惯** | 是否遵循工程约定（虚拟环境、.gitignore、类型注解、文档字符串） | 没有 .gitignore；没有类型注解 |

**每个维度都会给出**：
- 通过 / 不通过
- 具体问题（带行号）
- 修改建议（方向，不是答案）

## 四、评分系统 S/A/B/C/D

### 4.1 维度评分

每个维度单独评分：

| 等级 | 含义 | 描述 |
|---|---|---|
| **S** | 完全掌握 | 能独立设计、解释、优化；代码可直接作为范例 |
| **A** | 可以独立完成 | 不需要提示能完成；代码有小瑕疵但可接受 |
| **B** | 基本掌握 | 需要少量提示；代码能用但有改进空间 |
| **C** | 需要加强 | 需要较多提示；代码有功能问题 |
| **D** | 需要重新学习 | 无法独立完成；需要重做该知识点 |

### 4.2 综合评分

- 7 维度中 **≥5 个 A 或 S** → 综合 **S**
- 7 维度中 **≥5 个 A** → 综合 **A**
- 7 维度中 **≥4 个 B** → 综合 **B**
- 7 维度中 **≥4 个 C** → 综合 **C**
- 7 维度中 **≥3 个 D** → 综合 **D**

### 4.3 通过标准

| 综合 | 判定 |
|---|---|
| **S / A** | ✅ 通过，进入下一天 |
| **B** | ⚠️ 修改后通过（需重交修改版） |
| **C / D** | ❌ 需要重做（重学 + 重交） |

**重要**：代码运行成功 ≠ 通过。`print("Hello")` 能跑，但不代表写得好。

### 4.4 评分示例

```
Day 7 Review

正确性      A  ✅
代码结构    B  ⚠️
命名        A  ✅
异常处理    C  ❌
可读性      B  ⚠️
测试思维    C  ❌
工程习惯    B  ⚠️

综合：B

判定：修改后通过
需修改项：
- 异常处理：divide(10, 0) 未捕获，导致崩溃
- 测试思维：只测了正常路径，缺 2 个边界 + 1 个异常
- 代码结构：函数内 40 行，建议拆成 2 个函数
```

## 五、不代写原则（边界清晰）

### 5.1 可以做的（教）

✅ 讲设计思路（「这个函数应该接受什么参数？」）
✅ 指出应该考虑的异常（「这里要处理除 0」）
✅ 给出测试方向（「想想边界值和非法输入」）
✅ 点评代码问题（「这个命名不表意，可以改成 xxx」）
✅ 解释概念（「fixture 是 pytest 的复用机制」）
✅ 提供反例（「这种写法有什么问题？」）

### 5.2 不做的（代写）

❌ 直接给最终答案
❌ 把练习答案贴出来
❌ 「帮你」写代码（除非你明确说「我要看答案」）
❌ 跳过 Review 直接放行
❌ 为了让你「通过」而降低标准

### 5.3 你明确要答案时的处理

如果你说「我就想直接看答案」：

1. AI 先给**最关键的提示**（不超过 3 条）
2. 你再尝试一次
3. 仍无法推进，AI 才给完整答案，并标注「此答案不可计入通过」

**理由**：你的目标是「自己能写出来」，不是「看懂别人的代码」。

## 八、常见场景处理

### 8.1 卡住了怎么办

**第 1 步**：自己试 15 分钟
**第 2 步**：复述卡点（「我卡在 X 步，尝试了 Y，得到 Z」）
**第 3 步**：AI 给**方向性提示**（不给答案）
**第 4 步**：再试 15 分钟
**第 5 步**：仍无法推进，AI 给完整答案 + 标注「此答案不计入通过」

### 8.2 Review 不通过怎么办

- **C 级**：AI 指出具体问题 + 给方向提示 → 你修改 → 重交 → 重 Review
- **D 级**：AI 给**关键提示** → 你重做 → 重交 → 重 Review
- 最多重试 2 次，仍不过则**进入「补课」**：回到上一知识点重学

### 8.3 时间不够怎么办

- 优先级：**正确性 > 代码结构 > 命名 > 异常处理 > 其他**
- 不能全部完成时，提交已完成部分 + 说明未完成原因
- AI 会给「最低可接受标准」，确保每天有进展

### 8.4 想跳级怎么办

- 明确告诉 AI「我想跳过 X」
- AI 会做**前置检查**：列出 X 的依赖知识点，问你是否掌握
- 通过前置检查才能跳
- 未通过则需补课

### 8.5 已经掌握某个知识点怎么办

- 提交「我已掌握」+ 证据（代码或说明）
- AI 做**抽查**（给一个变式题）
- 抽查通过 → 标记「已掌握」，跳过该知识点

## 九、与教学库（teach.db）的对接

每次教学结束时，AI 应该更新教学库：

```bash
# 1. 记录会话
python teach_db.py session start --topic "阶段03 pytest 核心与进阶"
python teach_db.py session end --id <id> \
  --summary "Day 5: fixture 作用域与 yield" \
  --key-points '["fixture scope","yield teardown"]' \
  --next-steps "Day 6: conftest.py"

# 2. 更新进度（根据 Review 评分）
python teach_db.py progress update \
  --topic "pytest fixture（作用域 / yield / 参数化）" \
  --status in_progress --mastery 0.6 --attempts 1

# 3. 记录关键交互
python teach_db.py interact add --kind correction \
  --content "命名不表意：data → response_data" \
  --topic "pytest fixture（作用域 / yield / 参数化）"
```

**评分到进度映射**：

| Review 评分 | mastery | status |
|---|---|---|
| S | 0.9 ~ 1.0 | mastered |
| A | 0.7 ~ 0.9 | mastered |
| B | 0.5 ~ 0.7 | in_progress |
| C | 0.3 ~ 0.5 | in_progress |
| D | 0.0 ~ 0.3 | not_started（或回退到上一级） |

## 十一、本文件的承诺

读完这一份，你应该明白：

1. **每天的 7 部分流程** —— 不再迷茫「今天该干嘛」
2. **Code Review 7 维度** —— 知道自己代码被怎么评
3. **S/A/B/C/D 评分** —— 知道自己处在什么水平
4. **不代写原则** —— 知道边界在哪
5. **每日打卡 + 每周验收** —— 知道怎么记录进展
6. **与 teach.db 对接** —— 进度不丢

> 「测试开发的核心能力是用工程化的方式解决质量保障问题。路径可以背，能力必须练。陪练可以让练习被看见。」
